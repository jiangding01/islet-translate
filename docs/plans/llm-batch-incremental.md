# AI 批量翻译逐段提交与增量解析（体验债小批 #5）

> 状态：已实施（#83，见文末「实施记录」）。方案第 2 稿，2026-11-24 用户批准（第 1 稿经 Opus 对抗式审查，结论「需修改后批」，2 条阻断与 6 条重要项已改，见文末「审查记录」）。依据：`docs/reviews/2026-11-24-gemini-review-verification.md` 4.1 节（部分采纳的方案一）与第 6 节第 5 行；用户 2026-11-24 同意排进小批，并要求先写方案过审。M3e 的硬前置。

## 目标
用 AI 引擎（OpenAI 兼容、Gemini）整页翻译时，模型还在生成一批，某一段译文完整了就立刻显示，不再等整批 20 段全部生成完。对应 `docs/known-issues.md` 第 5 节「AI 引擎的整页翻译改为逐段出现」。

**成功标准**
- 长页面首批的第一段译文，在模型输出这一段之后约 50 ms 内出现在页面上，不等整批结束。
- 模型输出正常时，最终结果、缓存键、缓存内容与现在完全一致；提示词与 `PROMPT_VERSION` 不变，已有缓存不失效。
- 硬约束（前两条为审查裁决，第 3 条为 check 第 1 轮决定）：
  1. **顺序前缀**：只有序号恰好等于下一个期望值时才提前提交；第一次偏离后，本次尝试不再提前提交，剩余部分回到收尾时的整批校验。
  2. **缓存延后写**：只在本次尝试结束时写缓存。正常结束、截断或中断时，写入已提交的部分；出现编号异常时，这一批一条都不写。
  3. **只缓存经过整批校验的结果**（check 第 1 轮，2026-11-24 协调者决定，比第 2 条更严，以本条为准）：一次尝试只有在流读完、`finishBatch` 整批解码成功、已提交的段与整批结果一致时才写缓存；截断、中断、网络错误、限流、超时、取消、全部订阅者离开、`bad-response` 等其他结束方式一条都不写。提前分发的段照常留在页面上。

## 现状（调研结论）
```
content session.flush ──Port 帧 {id, 译文}──▶ 页面逐段渲染（本来就按段，16 ms 合批）
        ▲                                         （content 与协议都不用改）
        │ 每段 resolve 就发一帧（service.ts:369-385）
background service.run ── cache.getMany 命中直接发
        │
scheduler.submit ── chunkByLimits 拆 job（AI 每批 ≤20 段 / 3000 字）
        │  execute → collectItems 收齐全部 item ─▶ complete（写缓存）─▶ settle 一次性分发   ← 卡点 ②
        │
provider（openai-compat / gemini）SSE 流式累积 text ─▶ [DONE] 后 decodeLlmOutput ─▶ 逐个 yield item   ← 卡点 ①
```
- 卡点 ①：provider 收完全部 SSE 才解析（`openai-compat.ts:88`、`gemini.ts:92`）。
- 卡点 ②：调度器 `collectItems`（`scheduler.ts:210`）等所有 item 到齐，`complete` 统一写缓存、`settle` 统一分发（`:645`、`:471`）。
- `ProviderEvent` 已有 `{type:'item', index, text}`，接口形状不用变。

## 方案

### 1. 增量扫描器（`codec.ts` 新增 `createBatchScanner(sources)`）
纯函数，供两个 provider 共用。每收到一段 SSE 增量就 `push(delta)`，返回本次新确认的 `{index, text}`。扫描器有三种状态：**进行中**、**已关闭**（不再提交，但已提交的内容可信）、**受污染**（已提交的内容不可信）。
- **只从输出开头开始认**：允许开头是空白、一个完整闭合的 `<think>…</think>` 块（判定同 `createThinkFilter`，实现为逐字符状态机，不重扫累积串）、一个 ```` ```json ```` 围栏，之后第一个字符必须是 `[`。否则（开头是散文、缺开标签的推理等）直接关闭，全部交给收尾时的 `decodeLlmOutput`，行为与现在相同。
- 在数组里跟踪字符串、转义与花括号深度；每闭合一个顶层对象就 `JSON.parse`。
- **提交条件**，任何一条不满足就关闭（顺序前缀规则）：
  - 是对象，`i` 为整数，`i < 段数`，且**恰好等于下一个期望序号**；
  - `t` 是字符串且去空白后非空。
- **回声先压住**：`t` 与该段原文相同（规范化空白、不区分大小写）时不关闭、也不提交，先压住；等出现第一条与原文不同的项，再连同前面压住的一起提交。整批都是回声就一条都不提前提交。这样品牌名、数字这类本来就不用翻的短串不会让整批失去增量，而推理一开头就引用原文数组的情况（#75 的场景）也不会被提前显示。
- **遇到顶层 `]` 就关闭**，之后的内容不再提交（防止推理里先写 0–9、再写 10–19 这类拼接）。
- **受污染**：扫描器开始认数组之后，只要在字符串以外看到 `</think>`，或顶层数组闭合后还有除空白和围栏结尾以外的内容，就标为受污染。这说明前面认的可能是推理里的草稿。
- **疑似第二份答案**（`draft`，check 第 1 轮新增，第 2 轮收窄）：受污染的一种，指数组闭合后的尾部出现像第二个数组或对象的开头——`[` 之后（跳过空白）紧跟 `{`，或 `{` 之后（跳过空白）紧跟 `"`；输出结束时尾部还悬着一个 `[` 或 `{`、后面没有可判断的内容；或尾部出现 `</think>`（不区分大小写）；以及数组里字符串外出现 `</think>`。尾部只有散文时（包括 `item [1]`、Markdown 链接 `[docs](…)`、`{name}` 这类括号）只算受污染，不算疑似第二份答案。
- 每个字符只看一次：开头、数组内、数组后的尾部都用逐字符的小状态机，不累积字符串再整串重扫（check 第 1 轮）。

### 2. provider 收尾（`codec.ts` 新增共享函数，`openai-compat.ts`、`gemini.ts` 调用）
- 流式累积 `text` 的同时喂给扫描器，确认一段就立即 `yield {type:'item'}`。
- 收尾由一个共享函数 `finishBatch(scanner, text, count)` 处理，两个 provider 不各写一遍：
  - **整批解析成功、且已提交的段与整批结果完全一致**：按序号补交其余段，正常结束。唯一例外是扫描器标了「疑似第二份答案」：仍先补交其余段，再抛 `validation/bad-response`（宽松解码会优先取围栏或第一个数组，取到的可能正是草稿）。
  - **整批解析成功、但已提交的段不一致**：用整批结果补交其余段，再抛 `validation/bad-response`。剩余段都已有结果，不浪费请求；缓存一条都不写（见第 3 节）。
  - **受污染**：无论原来是什么错误（截断、中断、超时都一样），一律改抛 `validation/bad-response`。
  - **未受污染、数组没闭合**（输出在数组中途结束，例如 Gemini 流没有终止符、网关截断不报 length）：按截断处理，抛 `output-truncated`，剩余段二分；已提交的前缀不写缓存（第 3 条硬约束），二分后的半份各自成功时照常写缓存。
  - **未受污染、数组已闭合但条数不对、越界或重复**：说明模型合并或跳过了段，抛 `validation/bad-response`，一条缓存都不写。
  - 截断（`finish_reason==='length'`）、中断（没收到 `[DONE]`）、超出输出上限的现有判定不变，它们在已提交若干段之后照样抛出，再按上面的规则决定是否改抛。
- Google 引擎不是 LLM，不改。text 模式（划词卡片、快速翻译）不走提前分发，见第 3 节。

### 3. 调度器（`scheduler.ts`）
- `execute` 不再用 `collectItems` 收齐，改为逐个消费事件（只对没有 `stream` 的批量任务；text 模式的流式任务保持原路径，避免增量排到终稿之后）：
  - 按**本次尝试开始时的成员快照**把 `index` 映射到 segment，并按快照下标判重；不能直接用 `job.segments[index]`，成员会收缩；
  - 空译文仍判为该段失败（与 `complete` 现有规则一致）；
  - 其余立即 `deliver` 给订阅者，并 `release`（从去重表删除），同时从 `job.segments` 移出；
  - 记入本次尝试的「已提交」列表，尝试成功结束时才写缓存（回声译文照旧不写）；
  - 越界或重复的 index 照旧抛 `bad-response`；
  - job 不再处于 running（被 `expire` 或 `abandonIfOrphaned` 结束）后就停止消费，迟到的 item 不再分发。
- 尝试结束时，在 `execute` 里统一决定写缓存（check 第 1 轮改为只缓存校验通过的结果）：
  - 结果成功（流读完、整批校验通过）且 job 仍在 running：把本次尝试提交过的全部段**合并成一次** `persist`（提前提交的与收尾补交的一起）。`complete` 改为接收「segment 与译文」的配对，不再按 `job.segments` 下标取段；
  - 其他任何结束方式（`bad-response`、截断、中断、网络、限流、超时、取消、全部订阅者离开）：本次尝试**一条缓存都不写**，已提前分发的段照常留在页面上；
  - text 模式（带 `stream`）的任务同样只在成功、且 job 仍在 running 时写缓存。
  - 然后（job 仍在 running 时）把现有的重试、二分、超时逻辑**只作用于剩余段**；剩余为空时视为成功结束，`settle` 的 `done` 守卫保证不会重复通知。
  - 结束时再检查一次：快照里有没有既没提交、也没出错的段（缺 index），有就按 `bad-response` 处理。
- `expire`、`abandonIfOrphaned`、`split` 都遍历 `job.segments`，收缩后只作用于剩余段。
- 429 探测请求：部分段成功、最终失败时，不解除恢复状态（与现在「只有成功才算恢复」一致）。
- **提前释放去重表的代价**：一段提前分发、但缓存还没写的那一小段时间里，另一个标签页或页面重扫提交同样的原文，会再发一次请求。这种情况很少，不另加缓存表。

### 4. 不改的部分
- content 侧、Port 协议、`TranslateChunk` 格式、提示词、`PROMPT_VERSION`、缓存键、批大小（20 段 / 3000 字）、并发与超时参数。
- 首屏自适应小批：审查裁决为「观察」，等本 PR 真机测完首段时间再议。

## 拒绝的做法
- **FluentRead 式标记协议**（每段 BEGIN/END 标记，收齐后严格解析）：要改提示词，全部批量缓存失效；它本身也不做流式。只借鉴了「错位就整体拒收、不部分接受」的严格性：本方案在偏离后同样不再提前提交，交给整批校验。
- **只改 provider、不改调度器**：调度器仍收齐才分发，页面上看不到任何变化。没有更小的可用版本。
- **每 4 条或 100 ms 微批写缓存**：违反「缓存延后写」，且渲染即时性来自 `deliver`，与写缓存无关。

## 最脆弱的假设
本方案假设模型按顺序、边生成边把数组以 SSE 增量发出。如果某个网关把 SSE 攒到最后一次性发送，就没有提速效果，但行为与现在相同，不会出错。

**残余风险（写进已知问题；按 check 第 1 轮的新规则核对过缓存，见各条末尾）**：
1. **编号连续、内容错位**：模型合并或跳过了一段，但编号仍从 0 连续往下。顺序前缀规则挡不住，错位的译文会提前显示到别的段落下面。收尾时条数不对，整批判为 `bad-response`，缓存不写，剩余段二分重发。已显示的错位译文撤不回；页面会话的内存表（`session.ts` 的 `translations`）还可能把它用到同文的其他段落，直到点「显示原文」结束翻译或刷新页面。审查裁决只要求「错位不进缓存」，显示层的这个代价是换取逐段出现的前提。缓存：条数对不上时整批 `bad-response`，不写；在收尾之前被截断、中断、超时、取消打断时，新规则下同样不写（第 2 稿在这些情况下会写已提交的前缀，check 第 1 轮改掉）。成立。
2. **草稿与终稿不同**：模型开头就写出一个合法、顺序正确、又不是原文的数组，之后又给出另一份答案。受污染判定会让缓存一条不写，但已提前显示的几段同样撤不回。现有模型输出里没有观察到。缓存：第二份答案以数组或对象的形式出现（`[{`、`{"`，或输出末尾悬着 `[`、`{`）、含 `</think>`，或与整批解码结果不同时不写，成立；例外是第二份答案只用散文表达（数组后只有文字，括号也只是 `[1]`、`{name}` 这类），整批解码取到的仍是草稿，会写进缓存，这与改前整批解码的行为相同，不是本 PR 引入的。

上面两条的显示层问题已由 PR②「长度对照拦截 + 撤回重译」（#待补，`docs/plans/llm-batch-revoke.md`）处理：错位一批在提前显示前多数被长度对照拦下，整批校验失败时已显示的段由页面撤下并单段重译。剩下的残余风险记在该方案与 `docs/known-issues.md` 第 4 节。

## 测试
- **codec（扫描器）**：
  - 在每一个字符位置切分增量，结果都与一次性输入相同；
  - 字符串里有转义引号、`[`、`]`、`{`、`}`、换行、emoji；
  - 开头有闭合的 `<think>` 块、```` ```json ```` 围栏、空白时仍能增量；
  - 开头是散文、缺开标签的推理（`推理…</think>[…]`）、对象不是 `{i,t}` 时不提交任何段；
  - 序号乱序、跳号、越界、重复、`t` 为空时，从偏离处起不再提交；
  - 回声项先压住，后面出现非回声项时连同前面一起提交；整批回声不提交；
  - 顶层 `]` 之后再出现编号接得上的对象，也不提交；
  - 受污染：数组开始后出现字符串外的 `<\/think>`、数组闭合后还有散文，状态都变为受污染。
- **provider（openai-compat、gemini）**：用 `test-utils.ts` 的分块 SSE：
  - 第一段在 `[DONE]` 之前就 yield；
  - 收尾解析与已 yield 的段不一致：先补交剩余段，再抛 `bad-response`；
  - 截断、中断发生在已 yield 两段之后、未受污染：先 yield 两段，再抛原错误；
  - 同样的截断、中断、超时，但受污染（草稿数组后接 `<\/think>`）：改抛 `bad-response`；
  - 数组没闭合就结束（Gemini 无终止符）：抛 `output-truncated`；数组闭合但条数少：抛 `bad-response`。
- **scheduler**：
  - 提前到达的段在尝试结束前就分发给订阅者；
  - 缓存只在尝试结束时写**一次**，正常时包含全部段（提前提交的与收尾补交的合并）；
  - 截断后：已提交段写入缓存，剩余段被二分；
  - 编号异常（`bad-response`）：一条缓存都不写，剩余段按现有规则二分；
  - 重试与二分请求的文本只包含剩余段（断言 adapter 收到的 texts）；
  - 截止时间到：只有剩余段收到 timeout；
  - 所有订阅者离开、截止时间到、取消：已提交的段仍按规则写缓存，迟到的 item 不再分发；
  - 受污染或不一致（`bad-response`）发生在截断、超时之后：一条缓存都不写；
  - 索引按快照映射：二分后的半份 job 提前提交时不会错位；
  - 结束时缺 index：按 `bad-response` 处理；
  - 提前释放后同 key 再提交：会新建请求，不会挂起；
  - text 模式（带 stream 的任务）不走提前分发，增量与终稿的顺序不变。
- **service**：用真实调度器加一个可控闸门的分块 SSE（`service.test.ts` 已有 `sseResponse` 的用法），断言同一批的第一段 chunk 在该批最后一段到达之前就发出。这条替代 e2e。
- **不加 e2e**：e2e 的网络 mock 用 CDP 一次性返回整个响应，无法模拟分块到达；搭一个流式 LLM 的 e2e 环境超出本 PR 范围。逐段出现由 provider 与 scheduler 的分块测试保证，并通过真机验收确认。
- 全部跑 `npm run check` 与 `npm run test:e2e`（e2e 回归现有 Google 路径）。

## 真机验收（需要一个已配置密钥的 AI 服务）
- 用 DeepSeek 或其他 OpenAI 兼容服务整页翻译一篇长文章：首屏段落应该一段一段出现，不再一批 20 段同时出现。
- 用推理模型（会输出 `<think>` 的）翻译一次：不出现思考内容、不整页失败。
- 设置页「测试连接」与划词卡片照常工作。
- 不需要新的密钥或账号，用你已有的 AI 服务配置即可。

### 代码要点
- **`createBatchScanner(sources)`**（`codec.ts`）：逐个字符扫描，跟踪字符串、转义与花括号深度，每闭合一个顶层对象就 `JSON.parse`。开头用逐字符状态机扣掉闭合的 `<think>` 块（判定同 `createThinkFilter`），再允许空白与一个 ```` ``` ````／```` ```json ```` 围栏，之后第一个字符必须是 `[`，否则关闭、全部交给 `decodeLlmOutput`。对外暴露 `state`（`open` / `closed` / `tainted`）、`draft`（疑似第二份答案）、`array`（`none` / `open` / `closed`）与 `committed`。尾部判定也是逐字符状态机（空白、开头有围栏时至多三个反引号、再空白），不累积字符串。偏离（序号不等于下一个期望值、越界、`t` 为空或不是字符串、元素不是对象、JSON 不合法）后只停止提交，结构仍继续跟踪，用来判断数组是否闭合、输出是否受污染。回声（规范化空白、不区分大小写后与原文相同）先压住，遇到非回声项连同前面一起提交。
- **`finishBatch(scanner, text, count)`**（`codec.ts`，生成器）：整批解码成功时按序号补交未提交的段，与已提交的不一致、或扫描器标了 `draft` 时补交后抛 `bad-response`；解码失败时，受污染抛 `bad-response`，数组已开始但未闭合抛 `output-truncated`，其余照旧抛解码错误（扫描器没认出数组时与改前完全相同）。
- **两个 provider**：每个增量先喂扫描器，再做原有的截断、拦截、上限判定，然后 yield 本次确认的段。读流期间的任何错误（截断、中断、超时、取消、服务端错误）在扫描器受污染时改抛 `bad-response`。流结束后 `yield* finishBatch(...)`。text 模式不建扫描器，路径不变。
- **调度器**：没有 `stream` 的任务逐个消费事件，按尝试开始时的成员快照映射 index、判重；有效 item 立即 `resolveSegment`（`release` 并分发，空译文判该段失败）并从 `job.segments` 移出，记入本次尝试的配对列表。尝试结束后统一决定写缓存：只有结果成功且 job 仍在 running 时，才把配对合并成一次 `persist`（回声与空译文照旧不写；check 第 1 轮前为「结果不是 `bad-response` 就写」）。`handleResult` 的重试、二分、超时只作用于剩余段，剩余为空视为成功。`complete` 改收配对，`settle` 的回调改按 segment 取结果，写缓存拆到 `persist`。带 `stream` 的任务仍走 `collectItems`，收齐、刷完增量后再分发。
